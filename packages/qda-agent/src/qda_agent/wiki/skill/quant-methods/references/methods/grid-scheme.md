# grid-scheme
Search constraint: the row's menu (TASK.md) names the groups and symmetries it admits; one checkpoint stores every quantized module at one group and each format family at one symmetry, and bit width is what may differ per module. The W4A16 menu permits 4/8-bit modules; the W3A16 menu permits 3/4/8-bit modules, within the bpw ceiling and the serving-unit constraints. Promoted (wider) modules are stored symmetric.
Addresses: in-group outliers inflate a group's scale, a skewed group range wastes half of a symmetric grid, and few levels at a low bit width give a coarse step. Measured as: per group, absmax/rms, the skew (max + min)/(max − min) of its range, and the step size range/(2^b − 1).
Mechanism: Choose the integer grid: bit width (int4, int3, int8), group size (g32, g64, g128, or one scale per output channel), and symmetric or asymmetric (one int zero point per group). Smaller groups and a zero point both fit the grid closer to each group's range. At int3, lm_head and embed_tokens can stay on a wider grid (cond-head-embed-served-form).
Effect: a smaller group's range is at most that of the group it splits; a zero point removes the unused part of a skewed group's range, so its step shrinks by up to half; each extra bit halves the step; each of these raises the stored bits per weight.
Preconditions: the serving kernel must accept the scheme: Marlin takes int4 with or without a zero point and int8 symmetric only, at g32/g64/g128/per-channel; other bit widths serve sym only (Humming); the W4A8-FP8 CUTLASS path is sym only. Changing group size or adding a zero point changes bits per weight, so compare only at equal budget or state the budget change. A different grid for head and embedding needs them untied.
Inference overhead: none at a fixed grid beyond the kernel's zero-point handling: the same kernel serves symmetric and asymmetric g128.
Pitfalls: a container can carry a zero point that stores only zeros; the checkpoint then advertises an asymmetric scheme, pays the zero-point bits, and is symmetric in effect. Read the zero-point tensor, not the config field. Second: builds that differ in group size, zero point or head/embedding treatment are different formats; compute the budget from the saved tensors, not from the recipe. Third: packed zero points saved from a multi-process run must load identically to a single-process save, because the packing is per shard.
Origin: Dettmers et al. (SpQR) observed that second-order sensitivity in a weight matrix is partly structured in whole rows and columns. A smaller group gives a sensitive region its own scale, at the cost of more scale and zero-point metadata per weight.
Source: Dettmers & Zettlemoyer, "The case for 4-bit precision: k-bit Inference Scaling Laws", ICML 2023. https://arxiv.org/abs/2212.09720 (group size / data-type trade-off); small groups for structured sensitivity: Dettmers et al., "SpQR: A Sparse-Quantized Representation for Near-Lossless LLM Weight Compression", ICLR 2024. https://arxiv.org/abs/2306.03078 · code: https://github.com/Vahe1994/SpQR ; zero point: standard asymmetric integer quantization; head and embedding grid: cond-head-embed-served-form.
